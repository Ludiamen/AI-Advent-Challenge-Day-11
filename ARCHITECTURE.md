# Устройство агента

Документ отвечает на три вопроса: из чего агент собран, кто кому что передаёт и
почему разделение проведено именно так.

## Схема

```
   вопрос пользователя
        |
        v
  +-----------------+     правило 5: разбор реплики
  | MemoryManager   |---> Router (дешёвая модель) -> профиль / знания / решения
  | единая ЗАПИСЬ   |     правило 2: реплика -> краткосрочная
  +-----------------+     правило 3: шаг задачи -> рабочая
        |                 правило 4: завершение -> решения, рабочая очищается
        |                 правило 1: явное указание -> куда сказано
        v
  +-----------------+
  | PromptBuilder   |     единое ЧТЕНИЕ: отбор по стадии задачи
  | + трейс         |     возвращает сообщения И объяснение, что откуда взято
  +-----------------+
        |
        v
  +-----------------+
  | llm.Client      |     единственное место, где происходит HTTP-запрос
  +-----------------+
        |
        v
  +-----------------+
  | StateValidator  |     жёсткие инварианты — кодом; мягкие — дешёвой моделью
  +-----------------+     нарушение -> повтор -> эскалация модели -> отказ
        |
        v
    ответ + трейс + расход
```

## Хранилища

| Слой | Модуль | Где лежит | Срок жизни |
|---|---|---|---|
| краткосрочная | `agent/memory/short.py` | `память/диалог.db` (SQLite) | до очистки диалога |
| рабочая | `agent/memory/working.py` | `память/рабочая/<задача>.json` | до завершения задачи |
| долговременная | `agent/memory/long.py` | `память/долго/<кто>/профиль.json`, `решения.jsonl`, `знания.json` | пока идёт проект |

Разделение проведено по сроку жизни данных, а не по удобству кода. Отсюда и
разные технологии хранения:

* **SQLite для диалога.** Реплики дописываются часто, читаются хвостом и
  стираются целиком. Нужна атомарная дозапись и быстрый `DELETE` по сессии.
* **JSON-файл на задачу.** Состояние задачи должно переживать очистку диалога и
  подниматься через неделю. Отдельный файл читается `cat`, кладётся в git,
  переносится между машинами.
* **Три файла для долговременной памяти.** Профиль перезаписывается, решения
  только дописываются (потому и JSON Lines: дописать строку в конец нельзя
  «наполовину»), знания уточняются по идентификатору. Три разных режима записи —
  три разных файла.

## Кто за что отвечает

| Модуль | Ответственность | Чего НЕ делает |
|---|---|---|
| `agent/memory/short.py` | окно диалога | не решает, что запоминать |
| `agent/memory/working.py` | стадии задачи и разрешённые переходы | не ходит в сеть |
| `agent/memory/long.py` | профиль, решения, знания, отбор фактов | не вызывает модель |
| `agent/memory/router.py` | предлагает слой для свободной реплики | не пишет сам |
| `agent/memory/manager.py` | единственная точка записи + журнал | не собирает промпт |
| `agent/builder.py` | сборка промпта и трейс | не пишет в память |
| `agent/validator.py` | проверка ответа и переходов | не исправляет ответ |
| `agent/llm.py` | HTTP к провайдерам, повторы, лимиты | не знает про память |
| `agent/catalog.py` | модели и роли | не вызывает модели |
| `agent/seed.py` | начальные данные проекта | не нужен в проде |
| `agent/agent.py` | связывает всё и ведёт цикл ответа | не содержит знаний о ГИС |

Правило, которым проверяется любое изменение: **запись идёт только через
`MemoryManager`, чтение — только через `PromptBuilder`.** Если появляется соблазн
дописать что-то в профиль из `agent.py` напрямую, значит, не хватает правила
маршрутизации — и добавлять надо его, а не обход.

## Почему запись и чтение разведены

Соблазн объединить их в один класс «Память» велик, но тогда исчезает то, ради
чего день и задуман. Требование задания состоит из двух разных вещей:

* «явно выбирать, что и куда сохраняется» — это про запись, и ответ на него
  даёт журнал маршрутизации;
* «какие данные попадают в каждый слой» и «как это влияет на ответы» — это про
  чтение, и ответ на него даёт трейс промпта.

Один объект, который и пишет, и читает, отвечал бы на оба вопроса
«посмотрите в коде».

## Цикл ответа

1. `MemoryManager.route()` — стоит ли что-то из реплики сохранить надолго.
2. `MemoryManager.remember_message()` — сама реплика в краткосрочную память.
3. `PromptBuilder.build()` — сборка из слоёв по политике текущей стадии.
4. `llm.Client.call()` — вызов модели, выбранной по роли стадии.
5. `StateValidator.check()` — жёсткие инварианты, поиском по тексту.
6. При нарушении: повтор с напоминанием, затем эскалация модели на ступень.
7. `MemoryManager.remember_message()` — ответ в краткосрочную память.

Шаги 1 и 7 пропускаются, если соответствующий слой выключен: аблация должна
выключать слой целиком, а не только на чтение, иначе прогон «без короткой
памяти» всё равно наполнял бы её.

## Расширение

* **Новый слой** — модуль в `agent/memory/`, поле в `MemoryManager`, блок в
  `PromptBuilder` с обязательным `why`, строка в `POLICY` для каждой стадии.
* **Новый инвариант** — запись в профиле. Жёсткий обязан иметь значения, по
  которым его проверит код: `ProfileStore.add_invariant()` отклоняет жёсткий
  инвариант без значений, потому что непроверяемый запрет хуже отсутствующего —
  он создаёт ложное чувство защиты.
* **Новая стадия задачи** — `STAGES`, `TRANSITIONS`, `STAGE_LABELS`, `POLICY` и
  указание в `prompts.STAGE_INSTRUCTIONS`. Базовые четыре стадии убирать не
  стоит: детализировать их можно, а вот пропуск проверки перед завершением
  возвращает ровно ту недетерминированность, ради устранения которой автомат и
  заведён.
