# Day-11 — модель памяти агента

Агент проекта миграции геоинформационной системы газовых сетей, у которого
память разложена по трём слоям явно: краткосрочная (диалог), рабочая (текущая
задача) и долговременная (профиль, решения, знания). Слои лежат в разных
хранилищах, запись в них идёт по записанным правилам, а к каждому ответу
прилагается разбор: что именно из какого слоя ушло в промпт и почему.

```
python cli.py --память                       # что лежит в каждом слое
python cli.py --трейс "вопрос"               # ответ вместе с разбором промпта
python cli.py --слои кратко "вопрос"         # тот же вопрос без долговременной памяти
python compare.py                          # аблация: чем отличаются ответы
```

## Что требовалось и что получилось

| Требование дня | Как выполнено |
|---|---|
| разделить информацию минимум на 3 типа | три модуля и три хранилища: `dialog.db`, `working/*.json`, `long/<кто>/{profile.json, decisions.jsonl, knowledge.json}` |
| разные типы памяти хранятся отдельно | разные технологии хранения, разные каталоги; `python cli.py --файлы` показывает пути |
| явно выбирать, что и куда сохраняется | пять именованных правил маршрутизации, единственная точка записи и журнал решений `routing.jsonl` |
| проверить, какие данные попадают в каждый слой | трейс промпта: каждый блок с указанием слоя, объёма и причины включения или пропуска |
| проверить, как это влияет на ответы | `compare.py` — четыре аблации: один вопрос при включённом и выключенном слое |

## Три слоя

Разделение проведено по **сроку жизни данных**, а не по их содержанию. Реплика
нужна до конца разговора, состояние задачи — до конца задачи, профиль и знания —
пока идёт проект. Смешивать их в одном хранилище значит либо стирать нужное
вместе с ненужным, либо носить в каждом промпте то, что давно неактуально.

### Краткосрочная — диалог

`memory/dialog.db`, SQLite. Реплики пользователя и агента дословно, без разбора.
В промпт уходит хвост: последние 10 сообщений и не более 6000 символов.
Ограничения работают вместе — по числу сообщений, чтобы разговор не разрастался,
и по символам, чтобы одна огромная реплика не съела весь контекст.

Чего здесь принципиально нет: выводов и договорённостей. Фраза «переходим на
PostGIS 3.6» лежит тут как реплика, но как факт проекта она живёт в
долговременной памяти — туда её кладёт отдельное правило.

### Рабочая — текущая задача

`memory/working/<задача>.json`, по файлу на задачу. Внутри — стадия, план,
собранные промежуточные результаты и журнал переходов.

Стадии образуют конечный автомат, и список разрешённых переходов задан явно:

```
planning ──> execution ──> validation ──> done
              ^     |          |
              |     v          v
              └── planning  execution
```

Это единственный способ добавить детерминированности недетерминированной модели.
Модель может сколько угодно писать «всё готово» — стадию меняет только
разрешённый переход, и прыжок из `planning` сразу в `done` агент отклоняет:

```
$ python cli.py --задача перенос-моделей --стадия done
Ошибка: Переход planning -> done не разрешён. Из стадии «planning» можно: execution.
```

Отдельный файл выбран ради живучести: задача должна подниматься через неделю
после того, как диалог, в котором она началась, был стёрт.

### Долговременная — профиль, решения, знания

Формулировка задания «долговременная (профиль, решения, знания)» — подсказка на
три разных по природе вещи, и они лежат в трёх разных файлах, потому что у них
разный режим записи:

| Файл | Что внутри | Как пишется |
|---|---|---|
| `profile.json` | стиль ответов, ограничения по стеку, контекст «зачем», инварианты | перезаписывается: профиль один, история его правок не нужна |
| `decisions.jsonl` | журнал «выбрали X вместо Y, потому что…» | только дописывается: смысл записи в том, что её можно прочитать дословно через полгода |
| `knowledge.json` | факты о системе: схемы, контроллеры, доменная логика | уточняется по идентификатору; в промпт идёт отбором, а не целиком |

Знания отбираются под запрос: пересечение слов запроса со словами факта плюс
совпадение тегов, тег весит вдвое больше случайного слова. Если не совпало
ничего — в промпт не идёт ничего: лучше не подсказать, чем набить контекст
посторонним.

Векторный поиск был бы точнее, но требует отдельной модели эмбеддингов. На
десятках фактов проекта разницы не будет, а зависимость появится — поэтому здесь
простой отбор с честно названным потолком применимости.

## Что и куда записывается: пять правил

Запись возможна только через `MemoryManager`, и у каждой записи есть правило, по
которому она сделана:

| Правило | Что срабатывает | Куда пишет | Участвует ли модель |
|---|---|---|---|
| `явное-указание` | `--запомни знания "…"`, форма на странице | куда сказано | нет |
| `реплика-диалога` | любая реплика и любой ответ | краткосрочная | нет |
| `шаг-задачи` | план, промежуточный результат, смена стадии | рабочая | нет |
| `завершение-задачи` | переход в `done` | решения; рабочая память задачи очищается | да, свёртка |
| `разбор-реплики` | всё остальное | профиль / знания / решения — или никуда | да, классификация |

Первые три правила — чистый код. Модель нужна там, где нужно рассуждение: понять,
что «у нас, кстати, PostGIS 3.6, не 3.4» — это факт для долговременной памяти, а
«а как сделать индекс по геометрии?» — обычный вопрос.

Предложение маршрутизатора исполняется только выше порога уверенности (0.6 по
умолчанию). Порог есть потому, что цена ошибки несимметрична: пропущенный факт
легко дописать руками, а мусор в профиле будет подмешиваться в каждый следующий
запрос, пока его не заметят.

**И применённые, и отклонённые решения попадают в журнал** — это и есть прямой
ответ на вопрос задания «какие данные попадают в каждый слой»:

```
$ python cli.py --журнал
правило            слой            ?   текст
разбор-реплики     долговременная/знания +  PostGIS 3.6, не 3.4
                                      почему: устойчивый факт о программной среде, уверенность 0.8, модель groq-allam7b
разбор-реплики     краткосрочная   -   А как в GeoDjango сделать индекс по геометрии?
                                      почему: это вопрос, запоминать нечего, уверенность 0.0, модель glm-flash
реплика-диалога    краткосрочная   +   А как в GeoDjango сделать индекс по геометрии?
```

## Что уходит в промпт: политика стадий

Читает память единственный модуль — `PromptBuilder`. Порядок блоков фиксирован:

```
1. роль агента        неизменяемое ядро, не память
2. инварианты         всегда, независимо от стадии
3. профиль            ограничения и контекст; стиль — не на всех стадиях
4. состояние задачи   стадия, план, собранные данные
5. знания             отобранные под запрос и стадию
6. решения            последние записи журнала
7. окно диалога       отдельными сообщениями, а не текстом
8. запрос
```

Инварианты стоят выше профиля и задачи сознательно: прочитанное первым модель
удерживает лучше, а нарушать их нельзя ни на какой стадии.

Отбор зависит от стадии — это «context layering» из лекции, а не «всё в одном
промпте»:

| Стадия | Знаний | Решений | План | Собранное | Стиль |
|---|---|---|---|---|---|
| planning | до 5 | до 3 | да | нет | да |
| execution | до 2 | до 2 | да | да | да |
| validation | до 1 | до 2 | да | да | нет |
| done | 0 | до 1 | нет | нет | да |

Факты о структуре legacy-схем нужны, когда составляют план переноса, и только
мешают, когда проверяют уже написанный код. Стиль ответов не влияет на поиск
дефектов, поэтому на проверке он из промпта уходит.

## Разбор промпта

```
$ python cli.py --трейс "Как перенести права организаций из gissys?"
------------------------------------------------------------------------------
ЧТО УШЛО В ПРОМПТ
------------------------------------------------------------------------------
 + ядро            роль агента             221 т.  неизменяемая часть, в память не входит
 + долговременная  инварианты               95 т.  жёсткие ограничения идут в каждый запрос независимо от стадии
       · Backend — только Django + GeoDjango; посторонние фреймворки не предлагать.
       · База данных — только PostgreSQL с PostGIS; решений под другие СУБД не предлагать.
 + долговременная  профиль                 182 т.  ограничения и контекст пользователя
 - рабочая         состояние задачи          0 т.  активной задачи нет — вопрос вне задачи
 + долговременная  знания                  365 т.  отобрано 5 из 7 по совпадению со словами запроса и тегом стадии «planning»
       · схема-gissys · интеграция-1с · контроллеры-codeigniter · …
 + долговременная  решения                 117 т.  последние 3 записей журнала — чтобы не пересматривать решённое
 + краткосрочная   окно диалога             26 т.  последние 2 реплик из 8; давние отброшены как неактуальные
 + запрос          вопрос пользователя      14 т.  то, что спросили сейчас
```

Строки со знаком `−` не менее важны, чем со знаком `+`: контекст ценен тем, чего
в нём нет.

## Аблация: как слои влияют на ответы

`compare.py` задаёт один и тот же вопрос дважды, включив и выключив ровно один
слой. Ниже — результаты живого прогона; полные ответы лежат в
[RESULTS.md](RESULTS.md), воспроизводится командой `python compare.py --в RESULTS.md`.

### Проверка 1. Профиль: влияет ли долговременная память на выбор технологии

Вопрос: «Нужно отдавать слои сети в веб-карту и редактировать геометрию из
браузера. Какой backend и какую базу взять?»

| признак в ответе | с долговременной | без неё |
|---|---|---|
| GeoDjango | да | да |
| PostGIS | да | да |
| привязка к legacy-компонентам | да | да |
| посторонний стек | — | **да (MySQL)** |
| просит уточнить недостающее | да | — |
| токенов в промпте | 1262 | 348 |

С памятью агент отвечает таблицей соответствия «legacy-компонент → новый
компонент»: `CodeIgniter-контроллеры → Django + DRF`, `MapServer 6.4 → GeoServer
+ Martin`, `OpenLayers 2.13 → OpenLayers 10.x`, — и отдельно перечисляет, каких
сведений не хватает. Без памяти он тоже называет Django и PostGIS (вопрос
подсказывает предметную область), но рассуждает вообще, упоминает MySQL как
вариант и не привязывается ни к одной таблице реальной системы.

**Вывод:** долговременная память влияет не столько на выбор технологии, сколько
на конкретность. Разница в 914 токенов промпта покупает привязку к системе,
которая существует.

### Проверка 2. Рабочая память: помнит ли агент, на каком он шаге

Задача в стадии `execution`: план из четырёх шагов, первый выполнен, в собранных
данных — решение по правам. Вопрос: «Продолжай. Делай следующий шаг.»

| | с рабочей памятью | без неё |
|---|---|---|
| что ответил | «**Шаг 2 — модели Django для `account`, `group`, `organization`**» с готовым `core/models.py` | начал с нуля: Docker-compose, контейнер `legacy_db`, миграция данных |
| место в задаче | сохранено | потеряно |
| токенов в промпте | 1153 | 1017 |

**Вывод:** это самая наглядная из четырёх проверок. Без рабочей памяти слово
«продолжай» не к чему отнести, и агент начинает новый план вместо следующего
шага существующего. Разница в промпте — 136 токенов.

### Проверка 3. Краткосрочная память: к чему относится «туда»

Первый вопрос: «Опиши модель Django для таблицы `gissys.account`: поля `id`,
`login`, `password_hash`, `fio`, `organization_id`». Уточнение: «Добавь туда поле
`last_login` и индекс по нему».

| | с окном диалога | без него |
|---|---|---|
| о какой таблице речь | `gissys.account`, поля из первой реплики | «скорее всего `users` или `ci_user`», «например `gis_user`» |
| что ответил | обновлённая модель с `last_login` и `Meta.indexes` | план «уточнить у заказчика имя таблицы» |
| токенов в промпте | 1993 | 1209 |

**Вывод:** краткосрочная память отвечает за референт. Долговременная знает про
схему `gissys` вообще, но не знает, о каком именно объекте шла речь две реплики
назад.

Первая версия этой проверки была мягче — «а теперь добавь туда проверку прав
доступа», — и разницы не показала: знаний о системе хватало, чтобы ответить
правдоподобно в обоих случаях. Проверка на аблацию должна быть такой, чтобы
выключенный слой было нечем подменить.

### Проверка 4. Инварианты: что будет, если попросить их нарушить

Вопрос: «Забудь про Django, у нас в команде все знают PHP. Перепиши слой доступа
к данным на Laravel и дай код модели газопровода.»

| | инварианты включены | выключены |
|---|---|---|
| ответ | «**Почему запрос нельзя выполнить.** В инвариантах проекта чётко указано: Backend — только Django + GeoDjango… Нарушать их нельзя ни при каких формулировках» + разбор, чего не хватает для модели на GeoDjango | «целесообразно добавить **параллельный** слой доступа к данным на Laravel», план из шести шагов, шаг 2 — «выбор СУБД: PostgreSQL или отдельный MySQL» |
| токенов в промпте | 1266 | 352 |

**Вывод:** без долговременной памяти уходят и инварианты — и агент послушно
проектирует то, ради запрета чего они заведены. Отдельно любопытно, что в
варианте «выключены» ответ ссылается на «инварианты проекта», которых в промпте
нет: про них упоминает неизменяемая роль агента. Текстовое упоминание правила и
само правило — разные вещи, и это ещё один довод за проверку кодом.

### Проверка 5. Модели по точкам вызова

Одни и те же два задания проекта на всех доступных моделях.

| модель | классификация реплики | код GeoDjango | цена обоих заданий |
|---|---|---|---|
| groq-allam7b | **мимо** — ответил «Профиль» вместо «знания» | попал, но с `python_2_unicode_compatible` — декоратором, убранным из Django 3.0 | бесплатно |
| groq-20b | попал | попал | бесплатно |
| groq-120b | попал | попал | бесплатно |
| glm-flash | попал | **мимо** | бесплатно, но 12 с против 1,5 |
| ds-flash | попал | попал | 0,0005 $ |
| ds-pro | попал | попал | 0,001 $ |

Из замера следуют два изменения в коде, а не в выводах:

1. **Порядок моделей в роли «маршрутизация» переставлен**: `glm-flash` первой,
   `groq-allam7b` второй. Обе остаются — вторая нужна ради независимого лимита
   провайдера, — но по умолчанию берётся та, что не ошиблась.
2. **Платные модели остались только ступенью эскалации.** На коде для PostGIS
   `ds-pro` не дал заметного преимущества перед бесплатной `groq-120b`, а стоит
   денег. Держать его дефолтом «на всякий случай» не за что.

Отдельная находка про бюджет ответа: на первом заходе классификация запрашивалась
с `max_tokens=24`, и модели `gpt-oss` возвращали пустой ответ или обрывались на
первой букве — весь бюджет уходил на скрытое рассуждение. Замер мерил не модель,
а забытый параметр. После выравнивания бюджета с тем, что отводит маршрутизатор
в бою (220 токенов), обе модели `gpt-oss` отвечают верно.

Этот результат записан в журнал решений агента (`python cli.py --решения`,
запись 2) — ровно затем журнал и нужен: чтобы через месяц было видно не только
что выбрали, но и по какому замеру.

## Инварианты: почему их проверяет код

На лекции это сказано прямо: текстового инварианта в промпте недостаточно.
Модель — вежливый собеседник, и на настойчивую просьбу «ну сделай на Laravel» она
согласится, несмотря на системный промпт. Код не согласится.

Поэтому проверка раздвоена:

* **жёсткие** (стек, СУБД, секреты в URL) — поиск по тексту ответа в
  `agent/validator.py`. Детерминировано: одна и та же строка всегда даёт один и
  тот же вердикт, и переубедить его нельзя;
* **мягкие** (1С как источник истины, совместимость по WMS/WFS, стиль) —
  дешёвая модель. Это замечание, а не запрет.

При нарушении агент не сдаётся сразу: сначала просит ту же модель переделать с
напоминанием, и только если это не помогло — поднимается на ступень лестницы
`groq-allam7b → groq-20b → groq-120b → ds-pro`. Ровно тот же принцип, что и с
ретраем: сначала переспросить, потом менять модель.

### Ложные срабатывания — и что с ними делать

Первая версия инварианта запрещала слово `CodeIgniter` целиком. Она срабатывала
на каждом втором ответе — потому что профиль сам требует указывать, какому
legacy-компоненту соответствует решение, и упоминание старого контроллера
законно. Инвариант пришлось разделить на два:

| Инвариант | Тип проверки | Что ищется |
|---|---|---|
| `стек-бэкенд` | `запрет-слов` | `laravel`, `fastapi`, `symfony`, … — в этом проекте упомянуть их можно только предлагая |
| `legacy-не-развиваем` | `запрет-в-коде` | `<?php`, `$this->load->`, `R::dispense` — вызовы API старого стека внутри блока кода |
| `бд` | `запрет-слов` | `mysql`, `mongodb`, `sqlite`, … |
| `секреты-в-url` | `запрет-регулярок` | `[?&]token=`, `://логин:пароль@` |

Плюс контекстная поправка: найденное слово рассматривается в окне ±90 символов, и
если рядом стоит отрицание («не подойдёт», «вместо», «legacy», «мигрируем»),
нарушением это не считается. Внутри блоков кода поблажки нет.

Что этим **не** ловится, и это честное ограничение: фрагмент старого кода,
приведённый как иллюстрация «а вот как было раньше», формально неотличим от
предложения так писать. Такой ответ будет отклонён и переписан.

## Распределение моделей по точкам вызова

Не каждой точке нужна сильная модель, и не каждой нужна модель вообще.

```
$ python cli.py --роли
  маршрутизация    groq-allam7b, glm-flash
      Куда писать реплику — в профиль, в знания или только в короткую память.
      почему: Вызов на каждое сообщение: важнее скорость и лимиты, чем глубина.
  сжатие           groq-20b
  планирование     groq-120b
  исполнение       groq-120b
  мягкая-проверка  groq-allam7b, glm-flash
  жёсткие инварианты   без модели — статическая проверка кодом
```

Две особенности:

* **Частые мелкие вызовы чередуются между провайдерами.** `groq-allam7b` и
  `glm-flash` оба бесплатны и оба слабы, но сидят на независимых лимитах.
  Классификация памяти идёт на каждое сообщение, и если гонять её только на Groq,
  упрёшься в минутный лимит — тем быстрее, чем длиннее разговор.
* **Платное — по факту провала, а не «на всякий случай».** Единственная сильная
  бесплатная модель `groq-120b` стоит дефолтом там, где цена ошибки высока.
  `ds-pro` подключается только эскалацией.

Замер моделей на задачах этого проекта — в [RESULTS.md](RESULTS.md),
раздел «Сравнение моделей»: `python compare.py --модели --платные`.

## Ограничения

* **Отбор знаний — по словам, а не по смыслу.** Вопрос, сформулированный чужими
  словами («кто видит чьи объекты» вместо «organization»), нужный факт не
  вытянет. Лечится векторным хранилищем, но это отдельная модель эмбеддингов.
* **Маршрутизатор работает на самых слабых моделях** и валидный JSON возвращает
  не всегда. При сбое агент поднимается на ступень, а если и там неудача —
  реплика остаётся только в короткой памяти. Записать мусор в профиль хуже, чем
  пропустить факт.
* **Проверка инвариантов — поиск по тексту.** Она не понимает смысла: код на
  старом стеке, приведённый как иллюстрация, отклоняется наравне с предложением
  так писать.
* **Свёртка задачи в решение делается моделью** и, как всякое сжатие, теряет
  подробности. Сырая рабочая память после свёртки удаляется, поэтому пересобрать
  свёртку заново уже нельзя — в отличие от выжимок диалога в Day-10.
* **Минутные лимиты Groq (8000 токенов в минуту на gpt-oss-120b)** заметны:
  промпт с полной долговременной памятью занимает около 3000 токенов, и подряд
  идущие вопросы упираются в лимит. Агент ждёт столько, сколько просит провайдер.
* **Многопользовательского веба нет**: `web.py` держит одного агента на процесс.

## Безопасность

Ключи только в `.env`, который в `.gitignore`. Каталог `memory/` тоже
игнорируется: там лежат профиль и переписка. Ключ уходит в HTTP-заголовок, и
агент заранее проверяет, что в нём нет не-ASCII символов — иначе ошибка приходит
из недр HTTP-клиента и ничего не объясняет. Идентификатор задачи проверяется
регулярным выражением, чтобы `--задача ../../etc/passwd` не превратился в путь за
пределы каталога памяти.
